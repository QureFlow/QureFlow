# Release readiness

This development version has passing isolated DynamoDB Local integration tests, a successful frontend/backend build, zero vulnerabilities reported by the dependency audits at the time of execution, and actual browser verification with synthetic records. A read-only AWS check confirmed that the configured DynamoDB table is active and the clinic/doctor directories are readable (three clinics, ten doctors). Cognito app-client inspection was denied with `AccessDeniedException`. The new application has not been deployed; cloud mutations and live authentication flows remain untested. No real patient records were used or modified, and no cloud records or permissions were changed.

## Completed application protections

Verified sessions and authoritative database roles protect sensitive routes. Clinic/doctor scope and patient ownership are checked server-side. Patient queue responses redact other patients. Strict input schemas block role and password mass assignment. Login/recovery/registration limits, body-size limits, restricted CORS, security headers, generic server errors, and no-store responses reduce common exposure paths. Atomic visit/slot/current-consultation claims protect the tested concurrent operations. The frontend reports service failures instead of fabricating successful actions.

## Required before a live pilot

1. **Exercise Cognito in AWS staging.** Verify signup, confirmation, login, recovery delivery, expired/invalid access tokens, and pool/app-client settings with synthetic accounts. These provider flows were implemented but not called during local verification. Decide staff Cognito provisioning, MFA policy, and how unclaimed reception profiles become verified accounts. Signup and application-profile creation span two systems; add reconciliation for partial failures.
2. **Reconcile the existing DynamoDB table.** Back it up and migrate legacy profiles, duplicate contact details, patient-day claims, token locators, current-consultation claims, and slot counters before allowing concurrent traffic. Legacy scans support reads but do not retroactively establish all uniqueness invariants. Existing API clients must use the new authenticated paths.
3. **Validate the AWS deployment.** Confirm IAM transaction/condition-check permissions, Gateway routing, exact HTTPS CORS origins, trusted proxy handling, frontend builds, and secret management. Rotate any previously distributed development credentials. Production startup requires a unique signing key. The `/health` endpoint is liveness only; add an infrastructure readiness check and monitored alarms.
4. **Make operational recovery demonstrable.** Configure backups/PITR, retention, restore drills, structured monitoring, and controlled audit access. Current audit writes are transactional application records; the repository does not provide tamper-proof external log archival. Define a reception workflow for stale visits, end-of-day closeout, rescheduling, late arrivals, and no-show reconciliation.
5. **Load-test and migrate read models.** The local demo now uses transactionally maintained catalog, appointment, patient membership and clinic visit partition views, verified against its primary records. Run `npm run migrate:backfill --prefix backend` (a dry run) against the AWS table, resolve any reported identity conflicts, then apply it with `-- --apply --confirm-table=<table>`; it sets the activation marker only after a clean run; verify the `BatchGetItem` permission and historical date queries. Global/legacy scans and unpaginated API responses remain scaling work. Test peak multi-clinic load on AWS. Local in-memory rate limits are per-process; use Gateway/WAF or a distributed limiter across instances. Slot scheduling, doctor updates, and clinic/settings edits need a documented concurrency policy; settings/doctor/clinic edits currently allow last-write-wins updates.
6. **Validate the estimator on genuine operational observations.** Keep synthetic fixtures out of production. Evaluate prediction drift and error per doctor, arrival behavior, and whether the app actually reduces patient waiting in a pilot. The current synthetic validation scores demonstrate the pipeline, not effectiveness at a clinic. There is no clinical decision-making model or guaranteed wait time.
7. **Complete the product onboarding and privacy work.** Tenant onboarding, staff account management, retention/deletion workflows, notification consent and delivery, deployment support, and clinic-specific acceptance tests remain release work. Have the intended clinics review data handling and clinical workflows before using real records. This project does not claim HIPAA/DISHA certification or legal compliance.

SMS and WhatsApp delivery are not configured and their interface options are disabled. The Android app packages the same web interface; it has not been tested on a range of physical devices, and there is no validated offline clinical workflow. These limitations are explicit to avoid selling incomplete capabilities.
